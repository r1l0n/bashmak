# Проект «Башмак» — голосовой бот для Discord (CPU-only, multi-speaker)

> Исходное техническое задание: стек, обоснование выбора, ссылки на ресурсы,
> структура проекта и план реализации по этапам. Документ отражает замысел на
> старте; реализация местами разошлась с ним — актуальное состояние описано
> в [README.md](README.md).

---

## 1. Ключевое требование: параллельное прослушивание нескольких участников

Discord отдаёт голосовой поток **по каждому участнику отдельно** (RTP-пакеты
привязаны к SSRC — уникальному идентификатору источника). Это значит, что
смешивать всех в один поток не нужно и не следует — библиотека уже даёт
раздельные потоки, их просто нужно правильно развести по независимым
пайплайнам.

**Модель параллелизма:**

```
Discord Voice UDP
   │
   ├── SSRC user_A ──► AudioSink_A ──► VAD_A ──► STT_queue_A ──► [worker]
   ├── SSRC user_B ──► AudioSink_B ──► VAD_B ──► STT_queue_B ──► [worker]
   └── SSRC user_C ──► AudioSink_C ──► VAD_C ──► STT_queue_C ──► [worker]
                                                        │
                                                        ▼
                                          Общая очередь запросов к LLM
                                          (LLM — единственный shared-ресурс,
                                           т.к. на CPU параллельные инференсы
                                           одной модели убьют производительность)
                                                        │
                                                        ▼
                                              llama-server (1 инстанс)
                                                        │
                                                        ▼
                                          TTS worker ─┐
                                                       ├──► Output Arbiter ──► единый
                                          Music player ┘     голосовой выход в канал
                                                              (voice send — один поток;
                                                               арбитр решает: пауза музыки
                                                               на время ответа TTS, затем
                                                               resume)
```

**Output Arbiter** — небольшой компонент-регулятор единственного voice-send
потока: у TTS-ответов приоритет выше, чем у музыки. Если во время
воспроизведения трека приходит TTS-аудио — плеер ставится на паузу
(`voice_client.pause()` / сохранение позиции в yt-dlp-стриме), проигрывается
ответ, затем музыка возобновляется.

Асимметрия схемы:

- Приём (STT + VAD) параллелится нативно: каждый участник — свой таск asyncio,
  они не блокируют друг друга.
- LLM-инференс на CPU параллелить нельзя, 40+ ГБ RAM дают запас по памяти, но
  не по вычислению. Отсюда очередь FIFO с приоритетом по моменту окончания
  фразы.
- Ответ (TTS + voice send) сериализуется: в канал уходит один поток.

Реплики при этом не теряются, а становятся в очередь.

## 2. Стек технологий и обоснование

### 2.1 Discord-библиотека с приёмом голоса

**py-cord** — форк discord.py, в котором сохранена и активно поддерживается
функциональность приёма voice (`VoiceClient.listen()`, `sinks`), в отличие
от оригинального discord.py, где receive был вырезан.

- Репозиторий: https://github.com/Pycord-Development/pycord
- Документация: https://docs.pycord.dev/en/stable/
- Voice receive гайд: https://docs.pycord.dev/en/stable/ext/commands/api.html#voice

Даёт доступ к `AudioSink`, куда можно писать свой обработчик,
получающий PCM-фреймы **с привязкой к user_id** — это и есть точка входа
для параллельных пайплайнов по спикерам.

### 2.2 VAD (Voice Activity Detection) — нарезка речи на фразы

**Silero VAD** — маленькая (~1-2 МБ), очень быстрая на CPU, ONNX/torch.

- Репозиторий: https://github.com/snakers4/silero-vad
- Модель энкодирует чанки по 30-60 мс, даёт вероятность "это речь".

Нужен отдельный **инстанс VAD на каждого активного спикера** (или один
переиспользуемый по очереди — модель лёгкая, можно держать N инстансов
в памяти без проблем при 40 ГБ RAM).

### 2.3 STT (распознавание речи)

**faster-whisper** — реализация Whisper на CTranslate2, в разы быстрее
оригинального openai-whisper на CPU за счёт квантизации (int8) и
оптимизированного рантайма.

- Репозиторий: https://github.com/SYSTRAN/faster-whisper
- Модели (русский тянет хорошо от `small` и выше):
  https://huggingface.co/Systran (готовые конвертированные CTranslate2-модели)
- Рекомендация: `small` для скорости при нескольких параллельных спикерах,
  `medium` если качество важнее и участников обычно 1-2.

Каждый пайплайн-по-спикеру — свой экземпляр модели **или** общий пул
worker-процессов (multiprocessing), т.к. один процесс Python и GIL не дадут
реального параллелизма CPU-bound STT-инференса внутри одного процесса.

### 2.4 Обнаружение имени "Башмак" (wake word)

Обучать отдельную wake-word модель под русское слово — трудозатратно и
избыточно для старта. Прагматичное решение:

- STT уже транскрибирует всю активную речь (раз VAD её выделил).
- Простой текстовый фильтр: если в распознанной фразе встречается
  "башмак" (с учётом опечаток распознавания — можно через
  fuzzy-match, например `rapidfuzz`), то фраза целиком (или её часть
  после слова) уходит в LLM.
- Плюс: не нужно тренировать модель. Минус: чуть больше нагрузки на STT
  (транскрибируем всё, а не только после wake word), но при VAD-фильтрации
  тишины это не критично.

Библиотека для fuzzy-match: https://github.com/rapidfuzz/RapidFuzz

*Опционально на будущее*: если понадобится офлайн wake-word без постоянного
STT — **openWakeWord** позволяет обучить кастомное слово без глубокого ML-опыта.
https://github.com/dscripka/openWakeWord

### 2.5 LLM

**llama.cpp** в режиме сервера (`llama-server`), общение по HTTP
(OpenAI-совместимый API).

- Репозиторий: https://github.com/ggml-org/llama.cpp
- Документация по серверу: https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md

**Модель** — GGUF, квантизация Q4_K_M как баланс скорости/качества на CPU:

- **Qwen2.5-7B-Instruct-GGUF** — сильно рекомендуется для русского языка,
  хорошо держит контекст диалога:
  https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-GGUF
- Более быстрый вариант при нескольких одновременных участниках —
  **Qwen2.5-3B-Instruct-GGUF**:
  https://huggingface.co/Qwen/Qwen2.5-3B-Instruct-GGUF
- Альтернатива с хорошим RU — **saiga (ILYA GUSEV) на базе Qwen/Llama**:
  https://huggingface.co/IlyaGusev — поищи актуальный saiga_gguf релиз,
  модель специально дообучена под русские диалоги.

Запуск `llama-server` с числом потоков = число ядер CPU минус запас под
STT/VAD/TTS воркеры. Один инстанс сервера обслуживает очередь запросов
(см. раздел 1) — это и есть естественный throttling-механизм.

#### 2.5.1 Intent-роутинг (диалог vs команда музыки)

Перед полноценным диалоговым промптом реплика проходит лёгкую классификацию
намерения — чтобы "включи трек X" не превращалось в долгий разговорный
LLM-инференс, а обрабатывалось быстро.

Два варианта реализации (можно сочетать):

- **Regex/ключевые слова** ("включи", "поставь", "музык", "трек", "песн",
  "пауза", "стоп", "следующ", "громче/тише") — почти мгновенно, без LLM.
  Подходит как первый быстрый фильтр.
- **LLM с function calling / structured output** — если фраза не поймалась
  простыми правилами, можно попросить ту же модель (короткий системный
  промпт) вернуть JSON вида
  `{"intent": "music_play", "query": "название трека"}` или
  `{"intent": "chat"}`. llama-server поддерживает grammar-constrained
  вывод (GBNF) для гарантированно валидного JSON:
  https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md

Рекомендация для старта: regex-фильтр как быстрый путь, LLM-classification
как fallback для сложных формулировок.

### 2.6 TTS (синтез речи)

**Piper** — быстрый офлайн TTS, есть готовые русские голоса, работает на CPU
в реальном времени.

- Репозиторий: https://github.com/rhasspy/piper
- Голоса (включая русские): https://github.com/rhasspy/piper/blob/master/VOICES.md
- Модели голосов на HuggingFace: https://huggingface.co/rhasspy/piper-voices

### 2.6.1 Музыка

Отдельный модуль воспроизведения, который делит с TTS один и тот же
голосовой выход канала (см. раздел 1 — в канал одновременно можно слать
только один поток, поэтому музыка и TTS-ответы встают в общий "output
арбитраж": музыка на паузу → бот отвечает → музыка продолжается).

- **yt-dlp** — получение аудио-потока по названию/ссылке (YouTube и др.):
  https://github.com/yt-dlp/yt-dlp
- **FFmpeg** — обязателен, py-cord использует `FFmpegPCMAudio` для
  стриминга в voice channel:
  https://ffmpeg.org/
- Интеграция в py-cord: `discord.FFmpegPCMAudio(stream_url, **ffmpeg_opts)`
  подаётся в `voice_client.play()`.
  Гайд по voice playback: https://docs.pycord.dev/en/stable/api/voice.html

**Как распознаётся команда "включи музыку":** это не отдельный wake-word
хардкод, а intent, который определяет LLM (см. раздел 6.1 ниже) — так
бот может понимать команду в естественной форме ("Башмак, поставь
что-нибудь на фон", "включи трек такой-то"), а не только точную фразу.

### 2.7 Оркестрация / межпроцессное взаимодействие

- **asyncio** — основной цикл py-cord бота, обработка событий Discord.
- **multiprocessing / отдельные процессы** для STT-воркеров (CPU-bound,
  нужно уходить от GIL).
- **Очередь задач** — `asyncio.Queue` для внутрипроцессных, либо
  **Redis + RQ / Celery** если хочется отдельно масштабировать и
  переживать рестарты бота без потери очереди:
  - Redis: https://redis.io/
  - RQ (проще Celery для такого масштаба): https://github.com/rq/rq

Для старта рекомендуется **без Redis** — просто `asyncio.Queue` +
`ProcessPoolExecutor` для STT/TTS. Redis добавить, если проект будет расти
(например, разнести на несколько машин).

## 4. Поток обработки одной реплики (end-to-end)

1. Участник говорит в голосовом канале.
2. `AudioSink` пишет PCM-фреймы в буфер, привязанный к его `user_id` (SSRC).
3. `vad.py` для этого пользователя детектит начало/конец фразы (тишина N мс
   → конец фразы), передаёт готовый аудио-сегмент дальше.
4. Сегмент уходит в пул STT-воркеров (`ProcessPoolExecutor`) —
   параллельно с сегментами других пользователей.
5. Полученный текст проходит `wakeword/filter.py` — если "башмак" не найден,
   реплика просто логируется (по желанию, можно хранить как контекст
   разговора) и не идёт дальше.
6. Если wake word найден — формируется задача с `user_id`, `username`,
   текстом реплики → уходит в `intent/router.py`.
7. `router.py` определяет намерение:
   - **music_play / music_pause / music_skip / music_stop** — быстрый путь
     мимо основной диалоговой очереди: задача сразу идёт в `music/player.py`
     (поиск через `yt-dlp`, получение потока) → `Output Arbiter`.
   - **chat** — задача кладётся в `llm/queue_manager` (общая очередь к
     диалоговой LLM).
8. Для intent=chat: `queue_manager` берёт задачи по одной (FIFO), собирает
   промпт (персона + история диалога + текущая реплика с указанием, кто
   говорит), шлёт в `llama-server`, ответ → `piper_worker` синтезирует
   аудио.
9. Готовое аудио (TTS-ответ или музыкальный поток) поступает в
   `output/arbiter.py`, который сериализует единственный voice-send канала:
   если играет музыка и приходит TTS-ответ — музыка ставится на паузу,
   проигрывается ответ, музыка возобновляется.
10. Пока идёт обработка/воспроизведение — новые реплики из очереди ждут,
    STT/VAD при этом продолжают работать параллельно и не теряют речь.
