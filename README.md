# Башмак

Голосовой бот для Discord: слушает нескольких участников одновременно,
отзывается на своё имя, отвечает голосом и управляет музыкой. Работает
полностью локально на CPU — llama.cpp, GigaAM, Silero TTS, Silero VAD.

Целевое железо: Ubuntu x86_64, 6–10 ядер, 40 ГБ RAM. GPU не требуется.


---

## Установка

```bash
git clone <репозиторий> bashmak
cd bashmak
bash scripts/setup.sh --systemd
```

Первый запуск обязательно через `bash scripts/...`: при пуше с Windows бит
исполняемости в git-индексе не сохраняется. `setup.sh` проставляет его сам.
Зафиксировать бит в индексе один раз:

```bash
git update-index --chmod=+x scripts/*.sh
```

Скрипт ставит системные пакеты (`ffmpeg`, `libopus`, сборочные инструменты),
создаёт venv с зависимостями, разворачивает бинарники llama.cpp и качает веса
LLM, STT, TTS и VAD. Занимает 15–40 минут и около 15 ГБ диска, в основном под
модель. Повторный запуск безопасен: уже выполненные шаги помечаются `[skip]`.

### Флаги setup.sh

| Флаг | Назначение |
|---|---|
| `--profile balanced\|quality\|qwen\|vikhr` | Какие модели качать (по умолчанию `balanced`) |
| `--skip-models` | Только окружение, без весов |
| `--models-only` | Только докачать веса в готовое окружение |
| `--systemd` | Установить и включить юниты |
| `--vpn` | Поставить sing-box, запустить мастер настройки, включить маркировку трафика |
| `--tunnel` | Перегенерировать юниты с маркировкой трафика |
| `--with-whisper` | Докачать веса whisper — путь отката STT (см. «Распознавание») |
| `--force` | Пересобрать venv и llama.cpp, перекачать модели |

### Профили

| Профиль | LLM | Когда применять |
|---|---|---|
| `vikhr` | Vikhr-YandexGPT-8B (~4.6 ГБ) | По умолчанию |
| `balanced` | GigaChat-20B-A3B (~12 ГБ) | Запасной вариант |
| `fast` | то же | Алиас `balanced` |
| `quality` | то же | Алиас `balanced`, оставлен для совместимости |
| `qwen` | Qwen3-30B-A3B (~18 ГБ) | Шире общие знания и логика |

Столбца STT в таблице больше нет: распознаёт GigaAM, одинаковый во всех
профилях. Раньше профиль выбирал между whisper small и medium, то есть между
задержкой и точностью; выбирать стало не из чего — см. «Распознавание».

GigaChat и Qwen — MoE: из 20–30 млрд весов на каждый токен считаются около
3 млрд. По скорости это уровень плотной трёхмиллиардной модели, по качеству —
выше. В память при этом загружаются все веса, отсюда разница в размере файла;
при 40 ГБ ОЗУ она не критична.

Vikhr — плотная восьмимиллиардная, и меньший файл здесь ничего не ускоряет:
генерацию на CPU ограничивает не размер модели на диске, а сколько весов
читается из памяти на каждый токен, а их тут все восемь миллиардов против трёх.
На целевой машине `llama-bench -t 7` даёт 10.6 tok/s на генерацию и 65 tok/s на
разбор промпта — то есть около двух секунд на предложение и ещё столько же на
префилл при смене говорящего (пока говорит один и тот же человек, префилла
почти нет — см. «Кеш промпта»).

Выбрана она не за скорость, а за характер: это дообучение поверх pretrain-базы
YandexGPT, без корпоративного выравнивания, и персона из
[llm/persona.py](bashmak/llm/persona.py) проходит без отказов и извинений.
Взамен два тюнинга. `llm.temperature` снижена до 0.6 — карточка модели обещает
артефакты генерации на 1.0 и выше, а персоне высокая температура нужна, иначе
ответы вырождаются в три заготовки. И датасет у модели с Chain-of-Thought, так
что она тянет начать с преамбулы вместо ответа: `clean_reply()` оставит первое
предложение, но если первым окажется «так, давай разберёмся» — озвучится
именно оно.

GigaChat обучалась на русском с нуля, её токенизатор кодирует русский текст
примерно вдвое экономнее западных — при равных tok/s это вдвое больше
произнесённого текста. У Qwen3 шире знания и лучше рассуждения, но русский
текст обходится дороже в токенах.

Плотные модели крупнее 14B для голоса не подходят: 32B на десяти ядрах даёт
2–3 tok/s, то есть ответ из трёх предложений синтезируется полминуты.

Профиль определяет и состав загрузки, и пути в `config.yaml`. Смена после
установки:

```bash
./scripts/setup.sh --profile quality --models-only
```

После этого нужно поправить пути в `config.yaml`. Вместе с `llm.model_path`
проверьте `llm.prompt_format` (`gigachat` или `vikhr`): разделители ролей бот
подставляет сам, и с чужим форматом модель перестаёт видеть границы ходов —
запрос не падает, а ответы начинают уезжать в чужие реплики.

## Токен Discord

```bash
nano .env      # DISCORD_TOKEN=...
```

Токен создаётся на [портале разработчика Discord](https://discord.com/developers/applications),
вкладка **Bot** → *Reset Token*. Там же требуется:

- включить privileged intent **SERVER MEMBERS** — без него бот не видит ники;
- в **OAuth2 → URL Generator** выдать scope `bot` и `applications.commands`,
  права *Connect*, *Speak*, *Use Voice Activity*.

## Проверка и запуск

```bash
./scripts/doctor.sh
```

Скрипт печатает таблицу PASS/FAIL: системные пакеты, файлы моделей, ответ
`llama-server`, сквозной круг TTS → Whisper и валидность токена.

```bash
sudo systemctl start bashmak
journalctl -u bashmak -f
```

`bashmak.service` зависит от `llama-server.service`; оба юнита включены в
автозапуск и перезапускаются при падении.

## Обход блокировки Discord по IP

Диагностика:

```bash
curl -sS -o /dev/null -w 'connect=%{time_connect} tls=%{time_appconnect} code=%{http_code}\n' --max-time 10 https://discord.com/api/v10/gateway
```

`connect=0` означает, что SYN дропается и до TLS дело не доходит. Обход на
уровне DPI (zapret и аналоги) в этом случае бесполезен: он вмешивается в разбор
TLS ClientHello внутри уже установленного соединения, а соединения нет.
Требуется туннель.

Заворачивать весь сервер не нужно: `llama-server` слушает `127.0.0.1`, а
STT/TTS/VAD сети не касаются. Наружу ходит только бот — веб-сокет шлюза и
голосовой UDP, суммарно менее сотни килобит.

### Почему TUN, а не SOCKS

discord.py умеет проксировать REST и шлюз, но голосовой UDP-сокет открывается
напрямую, мимо настроек прокси. С прокси бот подключается к каналу и молчит в
обе стороны. Нужен виртуальный интерфейс, через который уходит весь трафик
процесса, включая UDP.

### Порядок настройки

**1. Inbound на VPS.** В панели (3x-ui и аналоги) завести **VLESS + TCP +
REALITY**, flow `xtls-rprx-vision`. XHTTP и другие маскирующиеся транспорты
добавляют джиттер, а голос чувствителен к разбросу задержки сильнее, чем к её
величине.

**2. sing-box на сервере.** Установка через `apt` с `deb.sagernet.org` в
заблокированной сети обычно не проходит: репозиторий на AWS и отваливается по
таймауту так же, как Discord. Ставится бинарником с GitHub:

```bash
sudo ./scripts/install_singbox.sh
```

**3. Подключение.** Мастер спрашивает параметры, проверяет их и поднимает
сервис:

```bash
sudo ./scripts/setup_vpn.py
```

Проще всего вставить ссылку `vless://` из панели целиком — все поля
разбираются автоматически. Ручной ввод тоже поддерживается.

Значения проверяются до записи в конфиг: опечатка в ключе Reality роняет
sing-box на старте с `illegal base64 data at input byte 12`, следом отваливается
туннель, Discord и бот, а выглядит это как проблема с сетью.

Шаги 2 и 3 объединяет `./scripts/setup.sh --vpn`: ставит sing-box, если его
нет, запускает мастер и прописывает маркировку трафика в юните.

Канал до VPS проверяется отдельно от маршрутизации через SOCKS-инбаунд из
конфига — ожидается `code=200`:

```bash
curl -sS --socks5-hostname 127.0.0.1:10808 --max-time 15 -o /dev/null -w 'code=%{http_code}\n' https://discord.com/api/v10/gateway
```

**4. Маркировка трафика.**

```bash
./scripts/setup.sh --tunnel
```

Юниты собираются из `deploy/*.template` в момент установки, поэтому после
правки шаблона или обновления репозитория `--systemd` / `--tunnel` нужно
прогонять заново — иначе в `/etc/systemd/system` останется копия от прошлой
установки.

[deploy/tunnel.sh](deploy/tunnel.sh) маркирует трафик по cgroup юнита, а не по
пользователю: отдельный пользователь и переразбивка прав на каталог проекта не
нужны, правило действует ровно на один сервис, ssh и apt остаются на прямом
маршруте. Локальные адреса и DNS из туннеля исключены, иначе бот потерял бы
собственный `llama-server` на `127.0.0.1`.

Состояние туннеля:

```bash
sudo ./deploy/tunnel.sh status
```

### DNS после поднятия туннеля

Если на машине перестало резолвиться всё подряд (`git`, `apt` пишут «Could not
resolve host»), sing-box зарегистрировал себя в systemd-resolved как резолвер
для линка `tun-bashmak` с доменом `~.`, то есть перехватил запросы всего хоста.
`tunnel.sh up` это снимает, но перехват возвращается при каждом перезапуске
sing-box. Разовое лечение:

```bash
sudo resolvectl revert tun-bashmak
```

Признак перехвата виден в `tunnel.sh status`: строка про DNS на туннеле должна
быть пустой.

После настройки туннеля `./scripts/doctor.sh` показывает `DISCORD_TOKEN`
зелёным — эта проверка первой упирается в блокировку.

## Использование

Бот входит в голосовой канал по команде `/start` и дальше реагирует на речь с
упоминанием имени.

### Slash-команды

| Команда | Действие |
|---|---|
| `/start` | Войти в голосовой канал вызывающего |
| `/leave` | Выйти из канала |
| `/status` | Состояние llama-server, очереди, музыки и задержек |

### Голосовые команды

| Пример | Результат |
|---|---|
| «Башмак, расскажи анекдот» | Ответ голосом |
| «Башмак, включи Кино Группа крови» | Поиск и воспроизведение |
| «Башмак, включи что-нибудь» | Бот выбирает трек сам |
| «Башмак, следующий» | Следующий трек |
| «Башмак, поставь на паузу» | Пауза |
| «Башмак, сделай потише» | Шаг громкости вниз |
| «Башмак, громкость 70» | Установка конкретного значения |
| «Башмак, выключи музыку» | Остановка воспроизведения |
| «Башмак, замолчи» | Обрыв ответа и остановка музыки без реплики |

Число в команде громкости распознаётся и словом: «громкость пятьдесят».

Имя может стоять в любом месте фразы — «включи Кино, Башмак», «включи Кино,
Башмак, пожалуйста». Имя вырезается, остальное уходит в обработку. Реплики без
имени игнорируются полностью.

Команда молчания распознаётся в вариантах «заткнись», «замолчи», «тишина»,
«стоп», «уймись» и ряде обсценных форм. По ней бот обрывает фразу на
полуслове, выключает музыку и не отвечает: ответ на такую команду был бы
очередной репликой. Вместе с этим сбрасывается очередь и контекст разговора.

### Поведение

- Диалог короткий: бот помнит последние несколько обменов в голосовом канале
  (`llm.history_turns`, по умолчанию три) и забывает их после двух минут
  тишины (`llm.history_ttl_s`). Глубина ограничена, потому что на CPU длинный
  контекст разбавляет вопрос и модель начинает отвечать на фон.
- Ответ всегда одно предложение.
- Ник говорящего уходит в системную часть промпта, а не в текст реплики. При
  подмешивании в реплику модель принимала ник за тему разговора.
- Пока бот говорит, музыка приглушается и затем возвращается к прежней
  громкости. Трек не останавливается и не теряет позицию.
- Название трека можно не называть: «включи что-нибудь», «включи музыку»,
  «поставь любую» — бот выберет сам. Выбор берётся не из головы модели, а из
  `music.random_sources` в конфиге: там строки-запросы и ссылки на плейлисты
  YouTube. Кубик кидается дважды — случайный источник, потом случайный трек из
  первых `music.random_pool` результатов выдачи.
- Из выдачи отсеиваются прямые эфиры, часовые миксы, Shorts и недавно
  игравшее. Главный фильтр качества — `music.random_min_views`: ноунеймы и
  ИИ-генерация отличаются от нормальной музыки порядком просмотров, а не
  словами в названии. Сверх порога отдельным списком выбрасываются
  бразильский фонк, явные ИИ-каналы и переливки чужого (nightcore, slowed,
  bass boosted) — их поиск по жанрам приносит сам, сколько бы просмотров у них
  ни было.
- Доиграв очередь, плеер продолжает сам (`music.autoplay`, по умолчанию
  включено) и объявлять треки не пытается: что играет, показывает `/status`.
  Радио заводится только после команды включить музыку и гаснет по «выключи
  музыку» — в тишине бот сам по себе не заиграет.

## Архитектура

```
Discord voice (по SSRC, раздельно на каждого)
   │
   ├─ sink.py ─ буфер ─ VAD ─┐
   ├─ sink.py ─ буфер ─ VAD ─┼─► пул процессов STT (параллельно)
   └─ sink.py ─ буфер ─ VAD ─┘            │
                                          ▼
                              wake word «башмак» (fuzzy)
                                          │
                                   intent-роутер
                              ┌───────────┴───────────┐
                         музыка                     диалог
                         (быстрый путь)      очередь к LLM (по одному)
                              │                       │
                              │                     Silero TTS
                              └────────┬──────────────┘
                                 Output Arbiter
                             (микс: речь + приглушённая музыка)
                                       │
                              один voice-send в канал
```

Приём параллелится по говорящим, инференс LLM — нет (на CPU это только
замедляет), выход тоже один. Реплики не теряются, а выстраиваются в очередь по
времени окончания фразы.

| Модуль | Назначение |
|---|---|
| [audio/sink.py](bashmak/audio/sink.py) | Приём PCM из voice-recv, разводка по говорящим |
| [audio/voice_recv_patch.py](bashmak/audio/voice_recv_patch.py) | Расшифровка DAVE и живучесть приёма поверх библиотеки |
| [audio/buffer.py](bashmak/audio/buffer.py) | Потокобезопасные буферы, граница «поток приёма ↔ asyncio» |
| [audio/vad.py](bashmak/audio/vad.py) | Silero VAD в onnxruntime, нарезка на фразы |
| [audio/listener.py](bashmak/audio/listener.py) | Опрос буферов, склейка VAD → STT |
| [stt/gigaam_worker.py](bashmak/stt/gigaam_worker.py) | GigaAM в onnxruntime, пул потоков |
| [stt/whisper_worker.py](bashmak/stt/whisper_worker.py) | faster-whisper в пуле процессов, движок отката |
| [wakeword/filter.py](bashmak/wakeword/filter.py) | Нечёткий поиск имени в тексте |
| [intent/router.py](bashmak/intent/router.py) | Регекс и LLM-фоллбэк: болтовня или команда |
| [llm/queue_manager.py](bashmak/llm/queue_manager.py) | Очередь к llama-server, один запрос за раз |
| [tts/silero_worker.py](bashmak/tts/silero_worker.py) | Silero TTS в пуле процессов, синтез по предложениям |
| [music/player.py](bashmak/music/player.py) | Очередь треков поверх микшера |
| [output/arbiter.py](bashmak/output/arbiter.py) | Единственный голосовой выход, даккинг музыки |

## Конфигурация

Все параметры — в [config.yaml](config.example.yaml): пороги VAD, размеры
моделей, число потоков. Промпт-персона — в
[llm/persona.py](bashmak/llm/persona.py).

### Распознавание

Распознаёт [GigaAM](https://github.com/salute-developers/GigaAM) — Conformer от
SberDevices на 240 млн весов, столько же, сколько у whisper small. Лицензия MIT,
веса в ONNX запускаются в том же onnxruntime, что и VAD.

Дело не в размере модели. Энкодер whisper всегда считает окно, дополненное до
30 секунд, поэтому реплика на две секунды обходится у него почти как на
двадцать. Conformer считает фактическую длину, а в голосовом чате почти все
реплики короткие — отсюда и берётся выигрыш. На русском при этом GigaAM
точнее: около 3.3 % WER у варианта `v3-e2e-rnnt` против 15–20 % у whisper
small. Суффикс `e2e` означает пунктуацию и нормализацию чисел; без него текст
приходит сплошной строчной лентой, и это заметно по ответам ЛЛМ.

Переключение движка — одна строка `stt.engine` в `config.yaml`, настройки
каждого лежат в своей подсекции. Веса whisper скрипт установки по умолчанию не
качает: `./scripts/setup.sh --with-whisper`, если путь отката нужен заранее.

Одноимённые ключи у движков означают разное. `min_avg_logprob` считается по
своей шкале у каждого, и значение от whisper сюда не переносится.
`stt.gigaam.threads` — общий пул onnxruntime на все одновременные
распознавания, тогда как `stt.whisper.cpu_threads_per_worker` задавал потоки на
воркера; см. бюджет ядер ниже.

### Бюджет ядер

По умолчанию рассчитан на 10 физических ядер: `llm.threads: 7`,
`llm.threads_batch: 10`, `stt.gigaam.threads: 3`, `tts.threads: 2`, VAD и
остальное — на основном лупе.

Сумма превышает десять, потому что считается пик одновременной работы. Этапы
одной реплики идут последовательно: распознавание, ответ, синтез. Пересекаются
llama-server и STT, когда бот отвечает одному участнику, а другой уже говорит:
7 + 3 = 10.

При whisper вторая строка бюджета была переподпиской: потоки задавались на
воркера, и двое говорящих давали 7 + 6 = 13 на десяти ядрах. У onnxruntime
`stt.gigaam.threads` — общий пул на все распознавания сразу, то есть потолок,
а не множитель, и от числа говорящих сумма больше не зависит. Если ядра есть,
это первый рычаг для задержки: поднимать до 6–8, сверяясь с бюджетом.

У генерации и разбора промпта разные ограничители, поэтому и потоков им
задаётся разное количество. Генерация упирается в пропускную способность
памяти, и отдача от потоков выходит на плато к шести-восьми — выше семи
наращивать `llm.threads` малополезно. Разбор промпта — обычное матричное
умножение, короткий всплеск на десятки-сотни токенов, и он масштабируется по
ядрам дальше; `llm.threads_batch` отдаёт ему все десять.

При торможении на трёх и более говорящих снижать нужно `llm.threads`, а не
`stt.gigaam.threads` — иначе распознавание перестаёт успевать и речь теряется
в буферах.

### Кеш промпта

Системная часть промпта — сотни токенов, и разбирать её заново на каждую
реплику дороже, чем сам ответ. llama-server переиспользует общий префикс
(`cache_prompt`), но ровно до первого отличия, поэтому:

- диалог и классификатор намерений считаются в разных слотах llama-server
  (`--parallel 2`): системные части у них разные, и в общем слоте каждый разбор
  намерения стирал бы кеш диалога целиком;
- заметка о говорящем в конце системной части держится короткой
  ([llm/persona.py](bashmak/llm/persona.py)): она меняется при смене участника,
  и всё, что стоит после неё — история и вопрос, — пересчитывается вместе с ней.

Пока говорит один и тот же человек, заново считается только новый вопрос.
Видно это по `journalctl -u llama-server`: в строке `prompt eval time` рядом с
временем стоит число разобранных токенов.

### Память

`llm.mlock: true` закрепляет веса в памяти. При 40 ГБ ОЗУ это бесплатно и
исключает сценарий, где часть модели вытесняется под page cache и читается с
диска посреди ответа.

## Диагностика

### Логи

Каждая реплика печатается одним блоком: распознанный текст, отправленный в
модель, ответ и длительность каждой стадии.

```
12:31:07 ┌─ участник ─ 3.8 с
│ слышу «Башмак, расскажи анекдот»
│ в ЛЛМ «расскажи анекдот»
│ ответ «Заходит как-то бот в голосовой канал...»
└─ ожидание 0.7 ██████  stt 0.6 █████  intent 0.0 █  llm 2.1 ███████████  tts 0.3 ███
```

Отсчёт идёт от момента, когда человек договорил, а не от начала распознавания.
Первая стадия — «ожидание» — это пауза, по которой фраза вообще считается
законченной (`vad.silence_ms` плюс запас: Discord перестаёт слать пакеты, когда
человек замолчал, и тишины, по которой VAD закрыл бы фразу, физически не
приходит). Стадия «очередь» появляется, когда реплика ждала своего инференса за
чужой: без неё это время выглядело бы как медленная LLM.

Отдельные стадии, реплики мимо бота и прочая механика пишутся на уровне DEBUG
(`logging.level: DEBUG`); там же в каждой строке появляются correlation id и имя
модуля.

Файлы: `journalctl -u bashmak -f` и `logs/bashmak.log` с ротацией.

`/status` показывает те же задержки медианой по последним репликам.

### Монитор

Отдельное окно с нагрузкой машины и задержками пайплайна:

```bash

```


Полосы уровня строятся по каждому говорящему: слева громкость входа, справа
оценка VAD рядом с порогом. Цвет задаётся оценкой VAD, а не громкостью — важно
не «шумно», а распознаётся ли звук как речь. Так видно, у кого тихий микрофон и
чья речь не добивает до порога.

Монитор работает отдельным процессом и читает пассивные источники —
`logs/turns.jsonl` (по строке на реплику, пишет сам бот) и `/proc`. IPC нет,
запускать и останавливать его можно в любой момент, в том числе по ssh.

Статистика считается по медиане и p90: одна десятисекундная реплика смещает
среднее настолько, что оно перестаёт быть показательным.

Имя модели берётся из командной строки живого `llama-server`, а не из
`config.yaml`: конфиг отражает намерение, cmdline — реально загруженную модель.
Значения расходятся, если сервер не перезапускали после правки конфига.

Стадия «речь» — длительность звучания ответа. Обычно это самая длинная часть
общего времени: реплика считается законченной после того, как фраза доиграет.
